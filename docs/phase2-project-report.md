# 在线问卷系统第二阶段项目报告

仓库：https://github.com/Day0God/DataBase/tree/homework01

## 摘要

第二阶段在原有在线问卷系统上增加了可复用题库、题目共享、不可变版本谱系、使用关系查询和单题跨问卷统计。实现保留第一阶段的账号、问卷状态、四类题型、条件跳转、答案校验、匿名控制、幂等提交和整卷统计，没有更换技术栈或重写系统。

本次新增 4 组题库集成测试，完整测试共 17 项，全部通过。测试证明题库改版不会改变已有问卷快照，共享用户可以使用但不能修改题目，恢复历史版本会创建新的后继版本，同一题目的回答可以跨问卷汇总。

## 1. 第二阶段目标

新增需求要求用户不必在每份问卷里重复编写相同题目，并允许团队共享。与此同时，已发布问卷和历史数据不能被题目库更新影响。因此本阶段需要同时解决可复用、权限、版本和统计口径问题。

交付目标包括：

- 保存、查找和复用常用题目。
- 建立命名题库。
- 将逻辑题目共享给其他账号。
- 保留题目版本历史和父子关系。
- 恢复历史内容而不覆盖现有版本。
- 允许不同问卷使用同一题目的不同版本。
- 查询题目在哪些本人问卷中使用。
- 对同一题目在本人多份问卷中的回答做统一统计。
- 保持第一阶段全部功能可运行。

## 2. 系统设计与增量原则

系统继续使用 Python、Flask、PyMongo、MongoDB 和原生 HTML/CSS/JavaScript。新增逻辑集中在题库 API、版本模型和题库页面；原有问卷填写与跳转解释器不变。

| 层次 | 第一阶段 | 第二阶段扩展 |
| --- | --- | --- |
| 前端 | 问卷列表、编辑器、填写、整卷统计 | 新增题目库页面和编辑器选题弹窗 |
| API | 认证、问卷、填写、统计 | 题库、共享、版本、使用关系、跨问卷统计 |
| 业务 | 跳转与答案校验 | 快照关联、版本谱系、所有权和共享权限 |
| 数据 | 五集合 | 新增三个题库集合，原题目集合增加可选来源字段 |

增量原则：

- 不删除第一阶段接口。
- 不改变 `questions` 作为问卷内快照的职责。
- 新字段均为可选，旧文档无需迁移。
- 新集合和索引在应用启动时幂等创建。

第一阶段的条件跳转和答案校验不做重写。从题库加入的题目先作为独立题目快照进入问卷，之后仍可在问卷编辑器中配置指向后续题目的跳转。提交时继续由 `evaluate_submission()` 从第一题重新遍历，执行必答、选项、文本长度、数字范围和整数校验，并拒绝未到达题目的额外答案。题库版本本身不保存跨题跳转，避免把 A 问卷的题目 ID 带到 B 问卷。

原有关系型业务限制继续有效：问卷发布中不能改题；已有回答的问卷关闭后可以重新开放，但题目保持锁定。第二阶段新增的题库操作不会绕过这些规则。

## 3. MongoDB 设计

### 3.1 新增集合

| 集合 | 职责 |
| --- | --- |
| `question_banks` | 用户自己的命名题库 |
| `library_questions` | 可复用的逻辑题目、所有者、当前版本和共享用户 |
| `library_question_versions` | 不可变题目快照、版本号、父版本和恢复来源 |

### 3.2 问卷题目快照

`questions` 继续保存问卷实际展示的完整题目，并增加可选字段：

```javascript
{
  libraryQuestionId: ObjectId,
  libraryVersionId: ObjectId,
  libraryVersionNumber: Number,
  libraryOwnerId: ObjectId
}
```

这些字段只用于追溯和使用统计。题目标题、选项和校验仍保存在问卷题目文档中，因此题库后续改版不会影响问卷。

### 3.3 索引

- `question_banks.ownerId + nameKey` 唯一索引，防止同一用户创建同名题库。
- `questions.libraryQuestionId + surveyId` 稀疏索引，支持使用关系和跨问卷统计。
- `library_questions.ownerId + updatedAt` 支持个人题目列表。
- `library_questions.bankId + updatedAt` 支持按题库筛选。
- `library_questions.sharedWith + updatedAt` 支持共享题目查询。
- `library_question_versions.questionId + versionNumber` 唯一索引，防止并发写入相同版本号。

## 4. 版本设计

每个逻辑题目有稳定的 `_id`，当前版本由 `currentVersionId` 指向。版本文档一旦创建不再原地修改。

```text
v1 创建
  │ parentVersionId
  ▼
v2 修改
  │ parentVersionId
  ▼
v3 恢复自 v1
  ├─ parentVersionId = v2
  └─ restoredFromVersionId = v1
```

恢复操作不会删除 v2，也不会把当前指针直接切回 v1，而是复制 v1 内容形成 v3。这样真正发生的操作仍然保留在历史中。

同一版本族不能改变题型，保证跨版本统计仍可比较。不同问卷在加入题目时可以选择任一可访问版本。

## 5. 共享与权限

题目所有者可以通过用户名将题目共享给其他用户。共享用户获得以下能力：

- 查看逻辑题目和全部版本。
- 将任一可访问版本加入自己的未发布问卷。

共享用户不能创建版本、恢复历史或改写所有者题目。问卷仍然是私有资源，只有问卷所有者可以编辑和查看整卷统计。

跨问卷统计只聚合当前用户自己拥有的问卷。这样可以区分“授权使用题目”和“授权查看回答”，避免题目共享导致其他用户回答泄露。

## 6. 从题库到问卷

编辑器点击“从题库添加”后：

1. 服务端返回当前用户可访问的题目。
2. 用户选择逻辑题目，再选择具体版本。
3. 前端复制该版本快照，生成问卷内新的题目 ID。
4. 保存问卷时服务端验证题库访问权和版本归属。
5. 只有题目内容与版本快照一致时，才保存来源字段。
6. 加入后形成的快照可继续参与第一阶段的条件跳转和答案校验。

如果用户修改了快照内容，来源关系不会被错误记录为某个原版本，题库本身也不会被修改。

## 7. 跨问卷统计

统计接口执行以下步骤：

1. 查询当前用户拥有的问卷。
2. 找出这些问卷中引用指定逻辑题目的题目快照。
3. 按可选题库版本筛选。
4. 从 `submissions.answers` 展开回答。
5. 按题型计算选项频数、文本内容或数字平均值、最小值、最大值。

统计响应包含使用问卷数、提交数、回答数、包含的版本和逐题结果。由于问卷保存独立快照，即使题库已经出现新版本，旧问卷的答案仍按原题结构解释。

## 8. AI 使用过程

本阶段继续使用 Codex 读取新增需求 DOCX，先提取八项用户反馈，再对照第一阶段代码设计增量方案。AI 参与了集合设计、版本状态建模、API、页面、测试和文档生成。

人工提出并确认的关键约束：

- 必须保留第一阶段系统和主要功能。
- 已发布问卷不能被题库改版影响。
- 需要同时保留历史版本和不同问卷使用不同版本的能力。
- 需要查询使用位置和跨问卷统计。

实施过程中采用的 AI 纠偏：

- 不将问卷题目改为实时引用题库，避免历史含义变化。
- 不用覆盖方式恢复历史版本，而是生成新的后继版本。
- 固定同一版本族的题型，避免跨版本统计不可比。
- 将跨问卷统计限制在本人问卷，避免共享权限扩大为回答数据权限。

## 10. 遇到的问题与解决

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| 直接引用题库会改变旧问卷含义 | 题库内容可变 | 问卷保存完整题目快照 |
| 恢复旧版本会覆盖当前历史 | 直接切换当前指针 | 恢复时复制历史内容生成新版本 |
| 不同题型共用版本导致统计失真 | 数据类型不可比 | 同一版本族禁止改变题型 |
| 共享题目可能扩大回答访问权限 | 使用权限与统计权限不同 | 跨问卷统计只包含本人拥有问卷 |
| 并发创建版本可能产生重复版本号 | 多个请求同时读取当前版本 | 版本号唯一索引和条件更新 |
| 第一阶段旧题目没有题库字段 | 历史数据早于新需求 | 字段全部可选，不强制迁移 |
| 题库题目加入跳转后跨问卷统计漏卷 | 来源校验误把问卷跳转视为快照差异 | 仅比较版本身份，允许问卷独立配置跳转 |

## 11. 已知限制

- 暂无题库删除和版本合并功能。
- 共享当前以单个用户名添加为主，尚未提供团队或用户组。
- 跨问卷文本回答一次返回当前统计范围的全部内容，大规模数据时应增加分页。
- 同一个逻辑题目的版本不能改变题型。

## 12. 结论

第二阶段在第一阶段系统上完成了题目复用、共享、不可变版本、历史恢复、使用关系查询和单题跨问卷统计。原问卷流程、条件跳转、校验、重复控制与整卷统计继续通过回归测试。实现符合“增量修改、不推倒重做、旧功能保持可用”的要求。
