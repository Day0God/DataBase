# 第二阶段需求实现记录

需求来源：根目录 `大作业一：需求增加.docx`

本阶段在第一阶段 Flask + PyMongo 系统上增量扩展，没有替换原有问卷、认证、填写、跳转、答案校验和统计流程。

## 1. 需求对应关系

| 新增需求 | 实现方式 | 验收位置 |
| --- | --- | --- |
| 保存常用题目并重复使用 | 新增用户题库和逻辑题目，支持四类题型 | `/library`、`/api/library-questions` |
| 创建问卷时从已有题目选择 | 编辑器新增“从题库添加”，可选择题目版本 | `/builder/<surveyId>` |
| 一道题被多个问卷使用 | 每份问卷保存独立题目快照，并记录题库题目与版本 ID | `questions` 集合 |
| 将题目共享给其他用户 | 逻辑题目保存 `sharedWith`，共享用户可查看和加入问卷 | `POST /api/library-questions/:id/share` |
| 修改题目不影响已发布问卷 | 题库版本不可原地修改，问卷使用加入时的快照 | 版本与快照一致性测试 |
| 查看题目版本历史 | 每个版本保存父版本与创建说明 | `GET /api/library-questions/:id` |
| 查看新版本由哪个版本改来 | `parentVersionId` 形成线性版本谱系 | 版本详情的 `versions` |
| 恢复旧版本 | 复制指定历史快照并生成新的当前版本 | `POST /api/library-questions/:id/restore` |
| 同一题目的不同版本同时存在 | 版本文档永久保留，问卷可选择任一可访问版本 | 编辑器版本选择器 |
| 查看题目被哪些问卷使用 | 根据问卷内题目快照的题库 ID 反查 | `GET /api/library-questions/:id/usages` |
| 建立题库 | 新增命名题库，默认自动创建“我的题库” | `/api/question-banks` |
| 题库中的题目更新版本 | 新版本创建后更新逻辑题目的当前版本指针 | `POST /api/library-questions/:id/versions` |
| 单题跨问卷统计 | 聚合当前用户各问卷的题库题目快照和回答 | `GET /api/library-questions/:id/stats` |

## 2. 兼容性约束

- 第一阶段现有 API 路径和请求格式保持可用。
- `questions` 集合继续承担问卷内题目快照，不改为远程引用。
- 第一阶段没有题库来源字段的题目仍按原方式读取、填写和统计。
- 新集合和索引由应用启动时的 `initialize_database()` 幂等创建。
- 不需要删除或重建第一阶段数据库。

## 3. 关键设计选择

### 为什么问卷保存快照

如果问卷只保存逻辑题目的 ID，题库一旦修改，正在填写和历史统计就会改变含义。因此问卷继续保存完整题目快照，并附加 `libraryQuestionId`、`libraryVersionId` 和版本号，用于追溯和使用关系查询。

### 为什么版本不可原地修改

每个版本是不可变历史记录。修改内容时追加新版本；恢复旧内容时也追加一个带 `restoredFromVersionId` 的新版本。这样现有的其他问卷、旧版本和使用关系都不会被覆盖。

### 为什么题库版本不能改变题型

同一题目的跨版本统计需要可比的数据类型。允许在单选、数字等完全不同的题型之间创建版本，会让聚合结果失去含义，因此版本只允许修改标题、必答状态、选项和该类题型的校验参数。

## 4. 权限边界

- 所有者：创建版本、恢复版本、共享题目、查看自己的使用位置和跨问卷统计。
- 被共享用户：查看题目与历史版本，将任一可访问版本加入自己的问卷。
- 问卷权限：问卷仍只能由其创建者编辑和查看统计。
- 使用位置：题目所有者可以看到所有问卷中的使用位置，共享用户只看到自己的问卷。
- 跨问卷统计只汇总当前用户自己拥有的问卷，避免共享行为变成回答数据访问授权。
